## 1. 结论

### 1.1 P1 出口 a：MTP 关 + W3 last_k 回到 W0 水平 ✅（G、E 节）
- direct-mock（11-02）对 qwen-current（10-31）四档按题合并：成功率 −4 点 [−16,+5]，Pass^2 −5 点 [−22,+10]，10 题升/降 2/2。
- 两边回忆都是 100%，复读 0/0，aborted 0/0，env 错均值 0.20–0.30 对 0.20–0.25。判：差在噪声内，P1「MTP 关后同一 harness 复测 4 档回到 W0 水平」成立。

### 1.2 W3 思考回放：不降成功率 ✅，峰值降幅量不出（G 节）
- 成功率同 1.1。实发峰值中位四档差 −167…+40 tok；轮内增长（峰值 − 首 prompt）904 → 818。
- 推断：按 10-31 记录的思考 token 量，hard 题每 run 4–5 次生成，last_k K=2 相对 all 预期只省约 55 tok，不到峰值的 0.5%——这套题量不出来。W3 的收益要在长轮（≥10 次生成）或 Gemma 卡禁回放上才看得见。

### 1.3 W-2 三档前缀（直调，H、E 节）
- prefix_base_tokens：mock 45 / prod 13,708 / catalog 5,280 / routed 5,280；L0 首 prompt 526 / 13,854 / 5,426 / 6,503。catalog、routed 比 prod 省 61% / 53%。
- 成功率相对 prod：catalog −5 点 [−22,+12]、routed −5 点 [−18,+7]，持平。prod 低于 mock：四档合并 21 点 [5,40]（p=0.031，E 节；含 16K 档，该档 direct-prod 有 3 行因前缀挤掉事实卡缺测），三共同档 0/32K/49K 为 17 点 [2,35]（p=0.12，H 节）。原因：prod 声明了而 harness 里只有桩的工具吃掉 21% 的调用（162/771 次回执 `Unknown tool`），这是 harness 形态的代价，不是前缀长度的代价（见 §2）。

### 1.4 P2 出口：不可判——编排器路径 L0 基线在地板（I 节）
- orch-turn-none 到 57K 没有拐点，但 L0 成功率只有 35%（Pass^2 20%）：拐点规则「≤ 基线 − 20 点」在基线 < 20 点时永远不触发，基线恰为 20 点时掉到 0 就「触发」——旧 verdict「orch-turn-w1 拐点 57344」只是 Pass^2 20% → 0%、两道题的事。两种都是空判；`analyze.py` 现在在基线 ≤ drop 时直接标「基线在地板，规则空判」（§2）。turn 放置三臂在 L0 处理完全相同，成功率却是 35 / 30 / 20%，这就是本批的噪声量级。
- 基线低的原因（M 节）：编排器路径 L0 就有 4–5/20 run 以「回合上限耗尽仍在发调用」中止（直调 mock 0/20、prod 1/20、10-31 qwen-current 0/20）——桩工具的失败调用、元工具（update_plan / complete_step）与护栏推回同计 max_total_iterations 熔断。
- 若把 57K 读作「拐点以上」：+W1 实发峰值 = level × 0.56、Σwall +3%（两项达标）；成功率比 0.57、Pass^2 0 / 11、回忆 91% → 0%（三项不达标）。+W1+W2：成功率比 0.19、Σwall +23%。
- 判：P2「拐点以上题集成功率 / Pass^2 ≥ 无管理 90%」不可判，不是不达标；全量重预填充「有账」成立（每 run 都有 `full_renders` 整数与逐轮 `turn_metrics`，N 节）。复测前须先把基线抬离地板（§3）。

### 1.5 W1 天花板活路径：按设计走了 fold，代价是轮内事实卡（J 节）
- 护栏开的两臂在 L57344：20/20 run 都在第 1 次生成前 fold（量得 56,823–58,249 → 发出 26,794–32,123）；超过 ceiling 53,248 的实发 0 次，实发最大 40,767；量法值与引擎计数在 3,189 次生成里全部相同（护栏量 2,396 次 + 代理自量 793 次）——引擎计数用的是同一分词器对同一渲染的 `len(ids)`，相等说明量法忠实复现了渲染，不是两套独立计数的交叉验证。L49152 每臂 hard 20 次（iteration 1），L57344 只有 w1 1 次 hard。context_guard 终止 0——FakeEngine 干跑预测的 abort 没出现，因为真引擎量法在首生成前就把 user 轮折进摘要。
- `peak_prompt_tokens` 行内字段里的 58,249 是 fold 前的量值（见 §2），没有发出去。guard off 臂有 1 个 run 第 10 次生成发了 65,538 tok 被 vLLM 拒绝（已先发到 63,479），这是关护栏的预期后果。
- 代价：57K 档回忆 91% → 0%——fold 把轮内填充连同事实卡一起压掉；之后 3 / 5 个 run 去调 rag_search（harness 里是桩），触发「检索未完成」拦截返回 System Error（w1 11 次 + 1 次调用解析失败、w1w2 20 次；直调四臂 System Error 均为 0）。天花板路径的正确性成立，但「当前 user 轮超限时折什么、留什么」是设计决定（§3）。

## 2. 口径缺陷与 harness 待修（本次复算的规避方式）
- `peak_prompt_tokens`（编排器模式）把护栏 fold 前的量值并进去了：w1、w1w2 各 21 行大于实发（中位 57,530，实发最大 40,767）。I 节一律用 gens 实发峰值。→ 修：行内 `peak_prompt_tokens` 只取实发，fold 前量值另记。
- fold 的 run 里 `fill.prompt_tokens_actual` 是压缩后的首次生成（29,297），不是填充实际量。→ 修：另记首次量法值。
- `analyze.py` 拐点规则在基线 < drop 时永远不触发、基线 = drop 时掉到 0 就触发（orch-turn-w1 的旧 verdict「拐点 57344」实际是 Pass^2 20% → 0%，只涉及两道题），两种都不报警。→ 已修：基线 ≤ drop 时 verdict 标「基线在地板，规则空判」（C / F / I 节 verdict 随之变化）。
- N 节「full_renders ≠ turn_metrics」「fill.prompt_tokens_actual ≠ 首生成」两列是同源回填，恒为 0，不是独立对账（「事件计数 ≠ 切片」一列是否同源未核）；编排器路径每次生成 0.79–1.00 次全量渲染、直调 0.56–0.69，原因未查（推断：编排器每步改 task_block / 工具集致前缀失配）。
- prod 前缀的桩工具把编排器基线压到地板（1.3 / 1.4）：harness 里 prod 声明的工具只有桩，真调用返回 System Error 并计入回合。→ 待定（§3）。
- `reused_prefix` 出现大于 prompt_tokens 的值（58,016 > 57,917）：vLLM num_cached_tokens 上报不可信，10-31 已知，照列不用。
