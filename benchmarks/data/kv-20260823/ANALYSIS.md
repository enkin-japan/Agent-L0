## 结论

### 1. 双针取回全绿——本探针灵敏度内无质量损伤，含 2.5 档
所有 20 个收官格 A/B 双针 3/3（含 2.5@64k，针 B 埋深 ~50%、距 query 3 万 token 级）。
口径限定：这是粗损伤探针（取回是/否），测不出 2026-07 概率探针发现的 2.5 档
「轻微退化」那种细粒度差异；两次测量不矛盾——2.5 档的细微质量税在取回类任务上
不足以翻针。

### 2. 省显存是 31b 长上下文独有的收益，MoE 26b 几乎白拿
- 31b（稠密架构）：64k 处省 2.5–2.8 GB（36.8→34.3/34.0），32k 处省 1.4–1.6 GB。
- 26b（MoE）：全档位省量 ≤0.4 GB——它的 KV 本身就小（KV 头少 + 滑窗层占比高），
  量化没什么可省。
- 3.5 与 2.5 的省量差别不大（KV 占峰值的比例本来有限），**若只为省显存，3.5 已拿走
  绝大部分收益**，2.5 的额外压缩不值得多冒质量风险。

### 3. 速度基本中性，26b 长上下文解码反而 +9%
- 26b@64k 解码 64.6→68.6（3.5）→70.3（2.5）tps：解码是带宽瓶颈，KV 读量变小直接
  变快。预填充 -2.5%（990 vs 1015，量化写入税）。
- 31b：解码 ±2% 内，ttft +1.6%（429.6 vs 422.7 秒@64k）。噪声级。

### 4. 🔴 交叉臂发现：KV 量化 × MTP 投机在引擎层不兼容
qwen38×3.5 两格同错：`TypeError: '_QuantizedStateProxy' object is not subscriptable`。
根因（读码定位，非猜测）：`mlx_vlm/models/qwen3_5/language.py` 的 MTP target-verify
退路注意力（`target_verify and L>1` 分支）对 `cache.update_and_fetch()` 返回值做
逐位置切片 `keys[:, :, :prefix_len+i+1, :]`；TurboQuant/Hybrid 缓存返回的是
`_QuantizedStateProxy`（只带 `.shape`/`__iter__`，量化态不可下标）。非投机路走整段
SDPA + 量化内核所以正常；dense KV 返回裸 `mx.array` 所以正常。
**生产含义：qwen38 的生产口径（entry 草稿 b5）今天不能开 KV 量化**；要开必须先做
引擎改造（verify 步注意力改走带 mask 的量化 SDPA，或 verify 前局部反量化），
是独立的引擎工作项，不在本测量波内动。

### 定档建议（供阶段四收口）
- **生产默认维持 dense**：26b 无收益；qwen38 被引擎不兼容挡死；31b 仅在 64k 且
  显存吃紧时值得开 3.5（省 2.5 GB + 解码不减速），做成场景开关而非默认。
- 2.5 档不进生产：省量相对 3.5 增益极小，质量余量却更薄。

> **订正（2026-08-23 阶段复审 m6）**：三处贴舍入边界的绝对断言按原始件收紧：
> ①31b@64k 3.5bit 省 **2.493G**（36.756→34.263；2.8G 是 2.5bit 档，

> （19.799→19.385），其余格成立。三条均不动结论方向。
