## 2. 头号结论：count 与 qa **59/59 全绿**

修复前满地的"秒终止/空样本"，修复后一格不剩。直接后果：

## 3. tool 列：又一处我方字节偏离（§S.17），非模型能力

逐字节对表发现工具**声明格式整个是另一套**：

| | 声明体 |
|---|---|
| 官方模板 | `<\|tool>declaration:get_current_time{description:<\|"\|>…<\|"\|>,parameters:{type:<\|"\|>OBJECT<\|"\|>}}<tool\|>` |
| 我方 | `<\|tool>{"name":…,"description":…,"parameters":{…}}<tool\|>`（JSON） |

外加三处结构缺陷（本波已修）：另开一个 `<|turn>system` 轮头、`<turn|><turn|>`
双闭合、工具间多余换行。此外同波查出三条更深的：声明在多 system 消息时发两遍、
无 system 消息时整个丢失、工具观测在重放里出现两次——均已修并补金测试。

**A/B 实证（同模型同问题，只换声明格式）**：

| 档 | 我方 JSON 声明 | 官方 DSL 声明 |
|---|---|---|
| 12b-4bit@0 | `<\|channel>thought<channel\|>` 无限循环，不调用 | `<\|tool_call>call:get_current_time{}` ✅ |
| e4b-8bit@4k | 幻觉"我已经获取了当前时间"，不调用 | `<\|tool_call>call:get_current_time{}` ✅ |

隔离实验排除约束采样：同 prompt 开/关 `tool_specs` 约束**都循环** → 病因在
声明格式而非 tool_guard。

**故「发现 C：e4b 长上下文工具服从性崩塌」亦告撤销**——不是 e4b 不听话，
是我们用它没见过的格式递工具。12B 的 tool 列几乎全挂同理。

> ⚠️ 本表 tool 列是**修字节缺陷前**跑的，且无论如何都受 JSON 声明体污染，
> 不构成模型能力证据；工具协议定案后须整列重测。count/qa 两列不受影响。

| 原发现 | 定性 | 真因 |

| B 31B 短 ctx 退化 | 曾判"模型级 mild" | 同上 |

## 5. 选型影响（**tool 列污染 ⇒ 一切质量比较暂缓**）

**全绿档有三个，不是一个**：26b-8bit 18/18、31b-4bit 18/18、31b-8bit 15/15
（64k 一格按 OOM 实证跳过）。

1. **26B 档**：8bit 全绿、4bit 16/18、qat-4bit 17/18——但差异**全部落在
   tool 一列**，而该列按 §3 自身的口径不作能力证据。**剥掉 tool 后三档在
   count+qa 上打平（12/12）**，这两支探针（数到十 / H₂O）也确实分辨不出真实
   质量差距。故 26B 缺省档之争**本波无法裁决**，留给 model_eval。
2. **31B 档**：PTQ-4bit **在速度与体积上决定性胜出**——比 qat-4bit 快
   33%(64k)~50%(4k)、权重小 9.7G、64k 峰值低 10.4G，且不像 8bit 那样 64k OOM。
   **但"质量更好"的话不能说**：三档在 count+qa 全平，tool 列不可用。
   原"31B 档 qat 替代 8bit"作废，改为：**PTQ-4bit 是速度/体积上的显然选择，
   QAT 是否值得那 33-50% 速度损失，等 model_eval 给质量结论**。
3. 口径自纠：初稿曾把 26b-qat@16k 的 tool 单点挂说成"抖动"、却把 31b-qat
   32k/64k 的同类挂当作"tool 更稳"的证据——同一个被污染的信号不能两头用。
   现统一：tool 列全部不作证据。
4. 12B 双档在工具场景**几乎全挂**（12b-8bit@32k 是唯一通过格），协议迁移后重评。
